# 先调研后建（dsh-research-then-build）

`/research <任务>` 进入一种工作方式，而不是启动一个独立流水线：**主 Agent 先分析、自己干活、流式输出；子 Agent 只在需要时被叫去跑一趟。**

## 谁在干活

| 谁 | 干什么 | 什么时候 |
|---|---|---|
| 主 Agent | 分析问题、拆能力点、写实现、解释理由 | 全程可见，流式输出 |
| 调研子 Agent | 检索现成方案，产出采购台账 | 需要外部事实时（`research_survey`） |
| 检查子 Agent | 挑刺：五个维度，给严重/建议清单 | 实现到可验收段落时（`research_challenge`） |
| 遗漏追问 Agent | 只回答一个问题：还有哪些地方没被覆盖 | 同上，与把握盘点并行 |
| 把握盘点 Agent | 只回答一个问题：哪些判断有把握、依据是什么 | 同上 |

子 Agent 的调用在对话里是一张工具卡片，所以进度是看得见的，而不是"命令执行中"一句话等到黑。

### 一次 `research_challenge` 问三个问题

三个问题**分开问、各自独立上下文**，因为混在一起时后两个会被第一个染上：

1. **挑刺**：按五个维度找会改变结论的问题，返回 JSON（`severe` / `minor`）。
2. **遗漏追问**（拿到第 1 问的发现清单）：只问"还有什么是没被覆盖的"——哪些文件没看过、哪些需求没验证、哪些结论只有说法没证据。明确要求不重复已有发现。
3. **把握盘点**（不依赖第 1 问）：只问"哪些判断你有把握、依据是什么"。

后两个并行跑，所以墙钟时间和一次差不多。追问没返回合法 JSON 时，报告会写"没有拿到遗漏清单"，而不是冒充"没有遗漏"。

## 用法

| 输入 | 作用 |
|---|---|
| `/research 给这个项目加上用户登录` | 进入先调研后建模式 |
| `/research-status` | 看当前处于哪一步、台账有没有、检查了几轮 |
| `/research-exit` | 退出，不交付 |

进入后主 Agent 会先把问题分析写给用户看，再动手。

## 三道门

1. **不许空手自研**：`research_finish` 在没有任何采购台账时直接拒绝。台账必须包含「## 能力点」段落和「结论：」行——结论要么是采用某个现成方案，要么是自研且落在三种例外之一（需求本质不匹配 / 许可证或合规不允许 / 集成成本可证明更高）。
2. **不许只自测**：`research_finish` 在没有任何独立检查时拒绝。检查由一个拿不到实现者推理过程的新 Agent 完成，它自己跑 `git status` / `git diff`、读代码，按五个维度挑刺：绕开台账 / 假证据 / 功能遗漏 / 未验证 / 过度设计。
3. **不许带着严重问题交付**：最后一轮还有 severe 且轮次没用尽时会退回，让主 Agent 先修。

最多 3 轮（可配到 6）。到上限后允许交付，但报告会把未解决的严重问题原样列出来。

### 门禁的边界（必须知道）

上面三道门的硬约束点在 `research_finish`。为了不让人绕过它，插件还订阅了 `agent/turn-stopping`（回合边界的串行拦截点）：一轮在没交付的情况下准备收尾时，监听器把一条提醒塞回 inbox，让这一轮继续。每轮最多提醒 2 次，进入新一轮时重置；用尽后放行。

所以"直接给结论就跑"会被拦下两次；两次都不理会才会漏过去。漏过去的标志是 `/research-status` 仍显示"进行中"——说明那次没走交付，也没有报告。

## 报告

`research_finish` 返回一份报告：任务、检查轮次、交付摘要、采购台账、每轮的问题计数、仍然存在的问题，以及最近一轮的**没被覆盖到的地方**与**有把握的部分**。同时写入 `$DSH_HOME/research-then-build/<会话 id>.json`，宿主重启后 `/research-status` 仍可查。

## 为什么不直接用 workflow 工具

DSH 自带 `workflow`（后台运行 + `workflow-run` 会话节点）确实能提供进度可见性，调研时对比过。不采用的原因：workflow 的中间值不进父会话，模型只拿得到最终结果；而这套要的是主 Agent 自己在对话里分析、实现、流式输出，子 Agent 只是被它按需调用。用 workflow 会变成"另一个运行器"，主 Agent 反而看不到过程。

真正没有现成替代品的是「独立评估者 + 交付放行」，这部分自研，并按硬门禁实现。

## 为什么不是一条命令跑完

v0.1 试过"命令内部跑整条循环"，两个问题：

- 命令执行有 ~90 秒上限，实测两次都在 90.0x 秒被 abort，跑不完一轮调研；
- 循环在命令内部，主对话没有可渲染的东西，用户只能看着"执行中"干等。

改成工具驱动后，两个问题都没了：工具调用可以长时间运行，且每一步在对话里留痕。

## 成本

花钱的不是插件自己的提示词（各 200~660 字符），而是**每次 spawn 都要重付一遍系统提示 + 工具 schema，再让子 Agent 自己读文件**。一次跑满 3 轮：

| 配置 | 子 Agent 次数 | 说明 |
|---|---|---|
| `probe: last`（默认） | 最多 6 | 1 调研 + 3 挑刺 + 收敛/末轮那次的 2 个追问 |
| `probe: every` | 最多 10 | 每轮都追问，结论更密但贵 40% |

省成本的三处：追问挪到收尾（`probe`）、检查者的取证边界（只读改动涉及的文件，不全仓扫）、台账只带最近 6000 字。

## 已知限制

- **工具按会话注册**。`/research` 时只给当前会话注册三个工具，其他会话看不到它们；注册后会立即校验可见性，环境不支持就回退全局注册（能力优先于省 token）。不在模式内调用会被拒绝并提示先进入。
- **门禁是硬的，但只硬在交付点**。`research_finish` 会比对工作目录指纹：如果独立检查之后代码又被改过，那份结论算过期，直接拒绝。主 Agent 仍然可以先写代码再调研，只要交付前补齐台账；也仍然可以在不调 `research_finish` 的情况下直接答复（见上文「门禁的边界」）。
- **指纹是启发式**：git 仓库用 `git status` + `git diff HEAD` + 未跟踪文件的内容哈希；非 git 目录退化成文件树（大小 + mtime）。它能发现"变过"，但不是密码学意义上的内容校验。
- **指纹在子 Agent 全部结束后才取**：这样它们在目录里留下的产物不会造成"复检→过期"的死循环。
- **插件重载后状态从 journal 回填**（`store.warm()`），所以收尾守卫在重载后仍然有效；重载本身会中断正在运行的子 Agent。
- **检查子 Agent 不是严格只读**。工具层只禁用了 `write` / `edit`，它仍可能通过 shell 改文件——与宿主权限模型一致，插件不额外改写审批策略。
- **实现由主 Agent 完成**，与主会话共享同一份工作目录，没有 worktree 隔离。
- **台账与检查输出都有形状校验**：格式不对会返回可操作的错误让模型重试，不会放行空台账或非 JSON 的检查结果。
- 同一会话同一时间只允许一次 `research_challenge`（避免轮次记账竞态）。
